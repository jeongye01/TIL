

### 📝 핵심 요약

| 구분 | **git checkout** | **git switch** |
| :--- | :--- | :--- |
| **주요 목적** | 다목적 (브랜치 전환, 파일 복원, 커밋 이동 등) | **브랜치 전환 전용** |
| **등장 시점** | Git 초기부터 존재 | Git **2.23 (2019년 8월)**에 도입 |
| **안전성** | 브랜치 전환 시 위험 요소 내포 (예: Detached HEAD) | 브랜치 전환에 최적화되어 **더 안전** |
| **파일 복원** | 파일 복원 기능 유지 (\`git checkout -- <file>\`) | 파일 복원 기능 **제외** (→ \`git restore\`로 분리) |
| **권장 사항** | **레거시** 명령어로 사용 지양 | **브랜치 전환 시** 사용 권장 |

---

## 1. \`git checkout\` (레거시/다목적 명령어)

\`git checkout\`은 Git 초기에 만들어져 **브랜치 이동**과 **파일 상태 복원**이라는 **두 가지 다른 역할**을 동시에 수행하는 **다목적** 명령어였습니다. 이 역할의 모호성 때문에 초보자들에게 혼란을 주었습니다.

### 주요 문제점:

* **역할 모호성:** \`git checkout <branch>\`는 브랜치를 바꾸는 것이고, \`git checkout -- <file>\`은 파일 내용을 되돌리는 것이므로, 하나의 명령어가 다른 종류의 작업을 수행합니다.
* **Detached HEAD 위험:** 특정 커밋 ID나 태그로 이동할 때 **Detached HEAD** 상태(현재 작업 위치를 가리키는 포인터인 HEAD가 브랜치 이름 대신 특정 커밋 ID를 직접 가리키는 상태)가 되어 브랜치 관리에 혼란을 줄 수 있습니다.

---

## 2. \`git switch\` (브랜치 전환 전용)

\`git switch\`는 복잡했던 \`git checkout\`의 기능 중 **오직 브랜치 전환(Branch Switching)** 역할만을 분리하여 전문화한 명령어입니다.

### 🔑 장점 및 사용법:

1.  **명확성:** 명령어가 **브랜치 전환**만을 의미하므로, 파일 변경(Restore)과의 혼동이 전혀 없습니다.
2.  **안전성:** 브랜치 전환에 최적화되어 Detached HEAD 상태로 전환되는 위험을 줄여 **더욱 안전하게** 브랜치를 전환합니다.

| 용도 | **git switch** 명령어 |
| :--- | :--- |
| **기존 브랜치로 전환** | \`git switch main\` |
| **새 브랜치 생성 및 전환** | \`git switch -c new-feature\` |

---

## 3. 🚨 \`git checkout\`의 역할 분리: \`git restore\`

\`git switch\`가 브랜치 전환 역할을 가져간 것처럼, \`git checkout\`의 **파일 복원** 역할은 **\`git restore\`**라는 새로운 명령어로 분리되었습니다.

이제 워킹 디렉토리나 스테이징 영역의 파일 변경을 되돌릴 때는 **\`git restore\`**를 사용하는 것이 권장됩니다.

| 이전 (\`checkout\`) | 이후 (\`restore\`) | 역할 |
| :--- | :--- | :--- |
| \`git checkout -- index.html\` | \`git restore index.html\` | 워킹 디렉토리의 파일 변경 취소 |
| N/A | \`git restore --staged index.html\` | 스테이징 영역에서 파일 내리기 (Unstage) |

### **⭐ 결론: 지금부터는 역할에 따라 구분하여 사용하세요**

| 상황 | **권장 명령어** |
| :--- | :--- |
| **브랜치를 전환/생성할 때** | \`git switch\` |
| **파일의 변경 사항을 되돌릴 때** | \`git restore\` |
